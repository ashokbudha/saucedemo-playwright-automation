# 3. Exploratory Testing

## 3.1 Objective

The objective of exploratory testing is to investigate the actual behavior of the SauceDemo application beyond predefined test cases. The exploration is intended to identify unexpected behavior, feature limitations, inconsistencies, and potential defects that may require further investigation.

Since formal product requirements and acceptance criteria are not available for the publicly hosted application, observations are not automatically classified as confirmed defects. Each finding is evaluated based on the available evidence and classified appropriately.

---

## 3.2 Exploratory Testing Approach

Exploratory testing was performed manually by interacting with the application and investigating both normal and unusual user flows.

The exploration included:

* Testing normal application workflows
* Trying different predefined user accounts
* Testing cart and checkout behavior
* Testing application state changes
* Investigating behavior outside the normal happy path
* Checking consistency between different parts of the application
* Recording unexpected or unusual behavior for further investigation

The findings from exploratory testing are documented below. Potential defects are kept separate from confirmed defects because the project does not have access to the application's formal requirements.

---

## 3.3 Exploratory Findings

### ET-001 — Product Quantity Cannot Be Modified

**Area:** Product / Shopping Cart

**Observation:**
Products can be added to the cart, but the application does not provide a mechanism to increase or decrease the quantity of an existing product. Quantity controls are not available on either the product page or the shopping cart page.

**Expected Behavior:**
The expected behavior cannot be formally established because no requirement was available stating that users must be able to modify product quantities.

**Classification:**
**Feature Limitation / Observation**

**Further Action:**
No defect is confirmed. The limitation should be considered when designing test scenarios and evaluating the application's functionality.

---

### ET-002 — Order Identifier Appears to Be Reused

**Area:** Order Placement

**Observation:**
The order identifier displayed after completing an order appears to be the same across different orders.

**Expected Behavior:**
The expected identifier-generation behavior is not formally defined in the available requirements.

**Classification:**
**Potential Issue**

**Further Action:**
Repeat the order process using separate orders and verify whether the same identifier is consistently generated. The exact label used by the application should also be recorded when documenting the finding.

---

### ET-003 — Order Can Be Placed with an Empty Cart

**Area:** Checkout / Order Placement

**Observation:**
A user can proceed through checkout and successfully place an order without adding any product to the shopping cart.

**Expected Behavior:**
An e-commerce order would normally be expected to contain at least one product. However, this expectation is not supported by an available SauceDemo requirement.

**Classification:**
**Potential Defect**

**Further Action:**
Record the behavior as a potential defect. Further evidence or an established business rule is required before classifying it as a confirmed defect.

---

### ET-004 — Reset App State Does Not Restore Product Button State

**Area:** Product / Shopping Cart / Reset App State

**Observation:**
After adding a product to the cart, the product button changes from **“Add to cart”** to **“Remove.”** When **Reset App State** is selected, the product is removed from the cart and the cart badge is reduced accordingly. However, the product button remains **“Remove”** instead of returning to **“Add to cart.”**

**Expected Behavior:**
Resetting the application state would reasonably be expected to restore the product's cart-related UI state so that the button reflects that the product is no longer in the cart.

**Classification:**
**Potential Defect**

**Further Action:**
Repeat the behavior with different products and verify whether the inconsistency occurs consistently. If confirmed, document it as a defect with appropriate evidence.

---

## 3.4 Findings Requiring Further Investigation

The following findings require additional investigation before they can be classified as confirmed defects:

| Finding ID | Finding                                               | Current Classification | Required Investigation                                                   |
| ---------- | ----------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------ |
| ET-002     | Order identifier appears to be reused                 | Potential Issue        | Verify identifier behavior across multiple independent orders            |
| ET-003     | Order can be placed with an empty cart                | Potential Defect       | Establish whether an empty order violates the intended business behavior |
| ET-004     | Reset App State does not restore product button state | Potential Defect       | Reproduce with multiple products and verify the UI/state inconsistency   |

The absence of formal requirements means that these findings should not automatically be treated as confirmed defects.

---

## 3.5 Summary

Exploratory testing identified several behaviors requiring consideration during further testing. These include a limitation in product quantity management, apparent reuse of order identifiers, the ability to place an order with an empty cart, and an inconsistency between cart state and the product button after resetting application state.

The findings will be considered when developing detailed test scenarios and test cases. Findings that can be sufficiently established as defects will be documented separately in the project's bug report.
