# 6. Bug Reports

This document contains defects identified during exploratory and functional testing of the SauceDemo web application.

Only findings that have been selected for defect reporting are documented here. Exploratory observations that are considered feature limitations or require further investigation remain documented in the exploratory testing documentation.

> **Note:** SauceDemo is a publicly hosted demo application, and formal product requirements or acceptance criteria are not available to the tester. Therefore, expected behavior in some defect reports is based on reasonable application behavior, consistency of application state, and standard e-commerce expectations. These assumptions are explicitly identified where applicable.

## 6.2 BUG-001 — Order Can Be Placed With an Empty Cart

### Bug Information

| Field           | Details                                |
| --------------- | -------------------------------------- |
| **Bug ID**      | BUG-001                                |
| **Title**       | Order Can Be Placed With an Empty Cart |
| **Severity**    | Medium                                 |
| **Priority**    | High                                   |
| **Status**      | Open                                   |
| **Type**        | Functional                             |
| **Area**        | Checkout / Order Placement             |
| **Source**      | Exploratory Testing — ET-003           |
| **Environment** | SauceDemo public web application       |
| **Browser**     | Google Chrome                          |
| **URL**         | `https://www.saucedemo.com/`           |

### Preconditions

* User is able to access the SauceDemo application.
* User is logged in with a valid user account.
* Shopping cart contains no products.

### Test Data

| Data          | Value           |
| ------------- | --------------- |
| Username      | `standard_user` |
| Password      | `secret_sauce`  |
| Cart contents | Empty           |

### Steps to Reproduce

1. Open the SauceDemo application.
2. Log in using valid credentials.
3. Do not add any product to the shopping cart.
4. Open the shopping cart.
5. Verify that the cart contains no products.
6. Proceed to checkout.
7. Enter the required customer information.
8. Continue to the checkout overview.
9. Click **Finish** to place the order.

### Expected Result

The application should prevent an order from being completed when the shopping cart contains no products.

The user should be prevented from placing an empty order and should receive an appropriate validation message or be redirected to a valid shopping state.

### Actual Result

The application allows the user to proceed through checkout and successfully complete an order even though the shopping cart contains no products.

### Impact

Allowing an order to be completed without any products can result in an invalid order state and may represent incorrect business behavior for an e-commerce workflow.

#### Evidence 1 — Empty Cart

The application is publicly hosted and formal business requirements are not available for this project. Therefore, the expected behavior is based on the reasonable e-commerce expectation that an order should contain at least one product.

This defect should be validated against the intended business rule if formal requirements become available.

## 6.3 BUG-002 — Reset App State Does Not Restore Product Button State

### Bug Information

| Field           | Details                                               |
| --------------- | ----------------------------------------------------- |
| **Bug ID**      | BUG-002                                               |
| **Title**       | Reset App State Does Not Restore Product Button State |
| **Severity**    | Medium                                                |
| **Priority**    | High                                                  |
| **Status**      | Open                                                  |
| **Type**        | Functional / UI                                       |
| **Area**        | Product / Shopping Cart / Application State           |
| **Source**      | Exploratory Testing — ET-004                          |
| **Environment** | SauceDemo public web application                      |
| **Browser**     | Google Chrome                                         |
| **URL**         | `https://www.saucedemo.com/`                          |

### Preconditions

* User is logged in with a valid user account.
* At least one product is available in the inventory.

### Test Data

| Data     | Value                 |
| -------- | --------------------- |
| Username | `standard_user`       |
| Password | `secret_sauce`        |
| Product  | Any available product |

### Steps to Reproduce

1. Open the SauceDemo application.
2. Log in using valid credentials.
3. Locate any product on the inventory page.
4. Verify that its button displays **Add to cart**.
5. Click **Add to cart**.
6. Verify that the product button changes to **Remove**.
7. Verify that the shopping cart badge displays `1`.
8. Open the navigation menu.
9. Select **Reset App State**.
10. Return to the product inventory page if necessary.
11. Observe the product button and shopping cart badge.

### Expected Result

After selecting **Reset App State**:

* The product should be removed from the shopping cart.
* The shopping cart badge should be cleared.
* The product button should return to **Add to cart**.
* The product and cart UI should represent the same reset application state.

### Actual Result

After **Reset App State**:

* The product is removed from the shopping cart.
* The shopping cart badge returns to `0`.
* However, the product button remains **Remove** instead of changing back to **Add to cart**.

This results in an inconsistent UI state where the application indicates that the product is removable even though the product is no longer in the cart.

### Impact

The inconsistent state can confuse users and may prevent the expected add-to-cart interaction for the affected product.

It also indicates that the reset operation does not completely synchronize the product UI state with the underlying cart state.

### Evidence

#### Evidence 1 — Product Before Adding

![BUG-002 Before Add](../evidence/BUG-002/01-product-before-add.png)

#### Evidence 2 — Product After Adding

![BUG-002 After Add](../evidence/BUG-002/02-product-after-add.png)

#### Evidence 3 — After Reset App State

![BUG-002 After Reset](../evidence/BUG-002/03-after-reset-app-state.png)

### Notes

This defect represents a state synchronization inconsistency between the shopping cart and product UI.

The behavior should be reproduced with multiple products to confirm whether the issue occurs consistently across the inventory.

## Bug Reporting Notes

### Relationship to Exploratory Testing

The defects documented in this file originated from exploratory testing:

```text
ET-003 → Investigation → BUG-001
ET-004 → Investigation → BUG-002
```

The exploratory testing document records the discovery and initial observation, while this document provides the formal defect report with reproduction steps, expected behavior, actual behavior, impact, and supporting evidence.

### Severity vs Priority

**Severity** represents the potential impact of the defect on the application or user experience.

**Priority** represents how urgently the defect should be addressed relative to other work.

For this project:

* **BUG-001** is classified as Medium severity because it allows an invalid application state but does not involve a real financial transaction.
* **BUG-002** is classified as Medium severity because it creates an inconsistent UI/application state.
* Both are given **High priority** because they affect core e-commerce workflows and should be investigated before considering the affected functionality reliable.

### Project Limitation

These defects are reported against the publicly accessible SauceDemo application. This project does not have access to the application's internal source code, backend implementation, development workflow, or official product requirements.

Therefore, the reports focus on observable application behavior rather than assuming an implementation-level cause.
