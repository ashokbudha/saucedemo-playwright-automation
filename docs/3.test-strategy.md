# 2. Test Strategy

## 2.1 Test Objective

The primary objective of testing the SauceDemo application is to evaluate the correctness, reliability, and usability of its key e-commerce functionality and to identify defects or unexpected behavior.

A major objective of this project is to use test automation to reduce the time and effort required for repetitive and frequently executed testing activities, particularly regression testing.

However, the project will not attempt to automate every test simply because it is technically possible. Automation candidates will be selected based on factors such as business importance, repetition, stability, test reliability, execution time, maintenance effort, and overall value.

The testing process will therefore combine **manual testing and automation**, using each approach where it provides the greatest value.

---

## 2.2 Test Scope

Testing will focus on the application's important and testable e-commerce functionality. The scope is selected based on factors such as business importance, frequency of use, repeatability, stability, and suitability for testing.

The following areas are included in the test scope:

* **Authentication**

  * Valid login
  * Invalid login
  * Locked-out user behavior
  * Other predefined user behaviors where applicable

* **Product Catalog**

  * Product listing
  * Product names, descriptions, prices, and images
  * Product sorting
  * Product detail pages

* **Shopping Cart**

  * Adding products
  * Removing products
  * Viewing cart contents
  * Cart item information

* **Checkout**

  * Entering required customer information
  * Validation of required information
  * Order summary
  * Price and total verification

* **Order Placement**

  * Completing an order
  * Order confirmation

* **Navigation**

  * Main navigation
  * All Items
  * Logout
  * Reset App State
  * Relevant navigation links

The project assumes that the application is sufficiently stable for the purpose of developing and evaluating a test strategy and automation suite.

---

## 2.3 Out of Scope

The following areas are deliberately excluded from the scope of this project:

* Real payment processing or financial transactions
* Payment gateway integration
* User registration and account creation
* Email or SMS notification testing
* Backend, database, or API testing where the required implementation access is unavailable
* Search or filter products

These areas are excluded because they either are not provided by the application, require access or infrastructure that is outside the project scope, or require specialized testing environments and techniques.

---

## 2.4 Test Types

The project will use a combination of manual and automated testing techniques.

### Functional Testing

Functional testing will verify that the application's features behave according to their expected behavior.

Examples include:

* Successful and unsuccessful login
* Product sorting
* Adding and removing products
* Checkout validation
* Correct order totals
* Successful order placement

### UI Testing

UI testing will verify important user-interface behavior and visible elements.

Examples include:

* Buttons and controls are displayed and usable
* Product information is displayed correctly
* Appropriate messages are shown
* Navigation leads to the expected page
* Cart information is updated correctly

### Regression Testing

Regression testing will be demonstrated through repeated execution of the automated test suite to verify that previously tested functionality continues to behave as expected.

Because this project uses a publicly hosted application and does not control its development or release cycle, the regression suite demonstrates the **capability for repeatable regression testing** rather than representing a production application's complete regression process.

### Basic Compatibility Testing

Selected important test cases will be executed across Playwright-supported browsers to identify basic browser-specific issues.

The initial browser coverage will include:

* Chromium
* Firefox
* WebKit

This is intended as basic browser compatibility coverage rather than comprehensive cross-platform compatibility testing.

### Exploratory Testing

Manual exploratory testing will be performed before and alongside automation.

The purpose is to:

* Understand application behavior
* Discover unexpected behavior
* Identify potential defects
* Explore areas not fully covered by predefined test cases
* Determine whether observed behavior is a defect, feature limitation, or expected behavior

Exploratory testing findings will be documented separately where appropriate.

## 2.6 Test Approach

Testing will follow a structured process that begins with understanding the application and gradually moves toward automation.

The overall approach is:

**Application Understanding**
-->
**Manual Exploratory Testing**
-->
**Defect / Observation Documentation**
-->
**Test Scenarios**
-->
**Detailed Test Cases**
-->
**Automation Assessment**
-->
**Automation Implementation**
-->
**Test Execution & Results**
-->
**Regression Suite**

Manual exploration will be performed before extensive automation so that the application's behavior is understood first.

Test scenarios will then be created to provide high-level coverage of the application's functionality. Detailed test cases will be developed for appropriate scenarios, including preconditions, test data, steps, and expected results.

After the test cases are established, each candidate will be evaluated to determine whether automation provides sufficient value.

Not every test case will automatically become an automated test. Tests may be:

* Automated at the UI level
* Automated at another appropriate testing level
* Kept as manual tests
* Excluded when they provide insufficient value for this project

This approach ensures that automation decisions are based on testing value rather than simply on whether a test can technically be automated.

---

## 2.7 Automation Strategy

Automation will focus on tests that provide meaningful value through repeatability, time savings, reliability, and maintainability.

Automation candidates will be evaluated using factors such as:

* Frequency of execution
* Repetitive nature of the test
* Business or functional risk
* Stability of the functionality
* Objectivity of the expected result
* Execution time
* Automation complexity
* Maintenance effort
* Expected lifespan of the test
* Overall return on investment (ROI)

High-value candidates are more likely to be automated, while tests that depend heavily on human judgment, are rarely executed, or require disproportionate maintenance may remain manual.

The project will also consider **the appropriate testing level** rather than assuming every test should be automated through the UI. Where applicable, broad data-driven or calculation-based testing would be more efficient at a lower level, while representative end-to-end scenarios can be covered through Playwright UI automation.

The automation suite will therefore aim to provide a focused set of reliable tests rather than maximizing the number of automated scripts.

---

## 2.8 Risks and Limitations

This project has several limitations that must be considered when interpreting its results.

* SauceDemo is a publicly hosted demo application and is not controlled by this project.
* The project does not control the application's development or release cycle.
* Changes to the public application may occur without notice.
* The application's backend, database, and internal implementation are not part of the project's controlled environment.
* The application does not represent a complete production e-commerce system.
* Real payment processing is not available for testing.
* Browser compatibility testing will be limited to the selected Playwright browser projects.
* Observed behavior without a clearly defined requirement may not be sufficient to classify something as a confirmed defect.

Therefore, the results and automation suite should be viewed as a **QA testing and automation demonstration against a publicly hosted application**, rather than as a complete production QA process.
